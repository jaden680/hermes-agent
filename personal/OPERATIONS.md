> 한 줄 원칙: **켜두고 · 쓰고 · 주 1회 다듬는다.** 다듬기(큐레이션)가 성패를 가른다.

---

## 1. 어디서 돌릴까 (런타임)
| 용도 | 권장 | 이유 |
|---|---|---|
| 개발만 | 노트북 `hermes -p work` | 그때그때 로컬 코드 경로 주며 작업 |
| 온콜·cron·Slack 상시 | **작은 VPS/홈서버 + systemd 상주** | 노트북 꺼져도 게이트웨이/크론 유지 |
| 둘 다(권장) | 상시 서버 1대에 work 프로필 → 노트북에선 SSH/TUI/Slack로 접속 | 데이터(`HERMES_HOME`)가 한 곳에 모여 메모리/학습이 안 쪼개짐 |

> 핵심: **데이터는 한 곳(HERMES_HOME)에 모은다.** 여러 기기에 흩어지면 자가학습이 분산된다.

## 2. 일상 리듬 ★

### 매일 (대부분 자동, 가벼움)
- 아침 브리핑(cron) 확인 → 오늘 우선순위 파악
- 온콜: Slack에서 봇에 질문 → **답변 초안** 받고, **내가 점검 후 직접 전송**
- 개발: "이 경로 작업해줘"로 로컬 코드 다룸
- → capture(적립)는 **자동**으로 일어남. 따로 할 일 없음.

### 주 1회 (15~30분) — 가장 중요한 운영 행위
이걸 빼먹으면 noise가 쌓여 답변 품질이 떨어진다.
```bash
hermes -p work          # 들어가서:
#  /skills   → 새로 생긴 런북 훑기 → 좋은 건 승격(아래), 이상한 건 삭제
#  /memory   → 적립된 사실 훑기 → 틀린 것 수정/삭제 (사람이 최종 권위)
```
- **좋은 런북 승격(Git 보존)**:
  `~/.hermes/profiles/work/skills/runbooks/<name>` → `personal/knowledge/runbooks/` 복사 후 커밋
- **카탈로그 갱신**: 새 서비스/결정 생겼으면 `service-catalog.yaml`에 반영 → 재인제스트
  ```bash
  hermes -p work -m "service-catalog.yaml 다시 읽고 메모리 갱신해줘."
  ```
- **Slack 학습**: 이번 주 좋은 장애/결정 스레드 1~2개만 선별 인제스트(capture-distill.md 2절)

### 월 1회 (30분)
- 메모리 가지치기(오래되거나 틀린 사실 정리)
- 사용량/비용 점검: `hermes -p work /usage`, `/insights --days 30`
- 백업 확인 + `doctor`

## 3. 비용·한도 운영
> **"두뇌는 좋은 모델/구독, 잡일은 싸게"**
- 메인 대화/개발/의사결정 → 구독(Claude Code) 또는 강한 모델
- 메모리 추출(hindsight) → `local_embedded`(로컬 임베딩 무료) + 추출 LLM은 싼 모델로 분리 가능
- cron/온콜 배치 → `hermes -p work cron create ... --model <싼모델>` 로 저가 지정
- 구독으로 돌리면 **주간 한도** 주시(비대화형 호출이 한도를 빨리 먹음)
- 모니터: `/usage`, `/insights`

## 4. 헬스·유지보수
```bash
hermes -p work doctor                         # 연동/도구 상태 (주기적)
systemctl --user status hermes-gateway        # 게이트웨이 상주 확인(서버)
tail -f ~/.hermes/logs/hindsight-embed.log    # 메모리 데몬 로그
hermes -p work backup                          # 스냅샷(야간 cron 권장)
git add personal/ && git commit && git push    # config/런북 버전관리
```

## 5. 품질·신뢰 운영 — "자율 답변"으로 가는 경로
지금은 **초안 모드**(사람 게이트). 신뢰는 단계적으로 연다:
1. 답변에 만족/불만족을 짧게 남긴다(👍/👎 또는 "이건 틀렸어 → 정정") → 메모리에 신호로 적립
2. **반복적으로 맞는 질문 유형/런북부터** 점진 자동화
3. 충분히 검증된 런북에 한해 자율 응답 허용(그 외는 계속 초안)
> 서두르지 않기. 자율화는 "이 유형은 90% 맞더라"가 데이터로 보일 때.

## 6. 가드레일 (운영 중 항상)
- 비밀/토큰/PII는 메모리·스킬·Git에 **넣지 않는다**(.env·원본 시스템에만)
- 외부로 나가는 메시지는 **사람 확인 후 전송**
- 자동 적립분은 **사람이 검토 후** 승격(사람이 최종 권위)
- 회사 코드는 **제이든이 준 로컬 경로**로만

## 7. 무너지는 신호 (안티패턴 — 보이면 교정)
- 주간 큐레이션을 거른다 → noise 누적 → 답변이 점점 헛소리
- 모든 호출을 비싼 모델로 → 비용/한도 폭발
- 카탈로그를 안 채운다 → 회수가 빈약해 일반론만 답함
- 메모리에 비밀이 들어간다 → 즉시 삭제 + 출처 차단

```
매일 : 그냥 쓴다 (학습은 자동). 온콜은 초안→내가 전송.
매주 : /skills·/memory 다듬기 + 좋은 런북 Git 승격 + 카탈로그 갱신   ← 핵심
매월 : 가지치기 + 비용점검 + 백업확인
항상 : 비밀 미적립 · 외부전송 사람확인 · 사람이 최종권위
모델 : 두뇌=구독/강모델, cron·추출=싼모델
```
